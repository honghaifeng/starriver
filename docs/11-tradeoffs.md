# 02 · 星河 StarRiver

`starriver/` · Node.js 22 · **零 npm 依赖** · 2050 行服务端 + 2123 行前端

> 本篇只讲设计取舍。接口、配置、计费、安全的完整参考在
> [`docs/`](./) 里的另外 10 篇，不重复。

## 为什么零依赖

99% 的项目在这个规模会上一堆包（express、axios、dotenv、body-parser…）。
这里一个都没有，全部用 `node:http` 和标准库。

| 理由 | 说明 |
|---|---|
| 部署环境在内网 | `npm install` 经常因为 registry 不可达失败 |
| 依赖会腐 | 半年后 `npm i` 装出来的东西已经和当时不一样 |
| 攻击面 | 一个 200 行的 express 中间件链，实际用到的不到 10 行 |

代价：路由、静态文件、body 解析、cookie、SSE 全部手写。
`server.js` 2050 行里有约 400 行是这些基础设施。

## 前端也是零构建

`public/app.js` 2123 行 + `style.css` 674 行，没有 webpack / vite / TS。

理由同上，加一条：**改一行 CSS 刷新就能看到**，不用等构建。
5 套主题（dark / light / bamboo / rose / …）全靠 CSS 变量切换。

> 提醒：默认主题是 dark。早期 dark 主题里有 27 个 CSS 变量写成自引用
> （`--sub: var(--sub)`），浏览器判定为无效值后**静默回落**，
> 导致所有灰色文字变成正文色、输入框没有底色、主按钮没有填充。
> 这类 bug 不报错、不告警，只能靠 `getComputedStyle` 断言抓。

## 三个必须知道的实现细节

### 撞输出上限必须显性报错

上游单次输出有硬上限。实测：`max_tokens=64` → 78 字就 `finish_reason=length`；
`8192` → 6862 字。一篇完整稿 5000–6500 字，5 篇约 2 倍上限，物理写不完。

早期版本把 `finish_reason` 整个丢弃，用户看到稿子停在半个标题上，
以为是模型能力不行。现在的处理：

```
pumpStream 采集 finish_reason
  → 撞 length 就自动续写（SB_MAX_CONTINUE，默认 2）
  → 续写后仍不完整 → done.truncated=true → 前端红字
```

**宁可显性报错，不做静默截断。** 一个用户能理解的失败，比一个看起来成功的失败好。

### 参考图转换必须三级兜底

`lib/ref-media.js`：

```
refToDataUri(file)
  → sips        （macOS）
  → ffmpeg      （Linux）
  → 原图直传    （兜底）
  → 全失败打日志
```

早期只调 `sips`。Linux 服务器上没有这个命令，于是每次**静默返回 null**，
参考图数组为空，悄悄退化成纯文生图。这个功能上线后从未真正生效过一次，
而界面上看不出来 —— 图还是生成了，只是没参考产品。

### 违禁词扫描的四个必须

| 要求 | 不做的后果 |
|---|---|
| 归一化（空格/零宽/间隔点/全角） | `抗 炎`、`激\u200b素`、`抗·炎` 全部漏检 |
| 位置回填原文 | 只能说「文中出现过」，不能高亮到那两个字 |
| 长词优先 | 「妇科疾病」会额外报「妇科」，命中数虚高 |
| 误报豁免 | 「第一步」「科普」被标红 → 用户两次之后学会无视它 |

**误报比漏报更致命。** 46 项断言里一半在验「不该报的绝对不能报」。

替换建议不是编的，全部取自客户《执行确认》里已列出的「我们建议的写法」。

**不自动改**：违禁词换成建议词后句子经常变病句，改稿得人看一眼。
所以「让它按建议改写」只把要求填进输入框，不自动发送。

## 多租户

所有查询带 `ownerId` 过滤。越权访问返回 **404 而不是 403** ——
403 等于告诉攻击者「这个 ID 存在但不属于你」，404 什么都不泄露。

`verify-tenancy.mjs` 用 89 项断言验这条，包括：
- A 用户拿 B 用户的会话 ID → 404
- 路径穿越 `../../etc/passwd` → 200/404（不是 500）
- 资产、上传、导出全部按 owner 隔离

## 数据落在 JSON 里

`data/db.json` 一个文件装全部业务数据：账号、会话、资产、台账、积分流水。

为什么不用 SQLite：星河的写频率低（一次对话几条记录）、读频率高（列表页），
JSON 全量读进内存后直接查，比 SQLite 快且没有 schema 迁移问题。

代价：
- 单文件损坏 = 全丢 → 每次写都先写 `.tmp` 再 rename
- 不能并发写多进程 → 单进程部署
- 文件会变大 → 资产元数据 + 会话全文，现在约 30MB
