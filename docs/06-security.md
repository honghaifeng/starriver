# 06 · 安全模型

> 这个产品处理的是客户的营销素材、内部账号和真实账单。
> 对外发布前，请把这一节当作出门前的检查清单，而不是"参考读物"。

## 1. 威胁模型

我们假设的攻击者能力（按现实排序）：

| # | 谁 | 想干什么 | 我们怎么挡 |
|---|---|---|---|
| 1 | 拿到链接的陌生人 | 白嫖模型调用 | 必须登录；余额/额度双闸门 |
| 2 | 同一组织的普通成员 | 看同事的文案、删同事的图、把消耗记别人头上 | `ownerId` 逐条隔离 + 越权 404 |
| 3 | 被停用的离职员工 | 用旧 Cookie 继续用 | 每次请求回查 `status` |
| 4 | 猜密码的人 | 撞库 | scrypt 哈希 + 5 次锁定 + 同提示防枚举 |
| 5 | 普通管理员 | 给自己升所有者、动所有者账号 | 角色变更只有 owner 能改；admin 不能建 admin |
| 6 | 拿到文件名的人 | 猜导出件 URL 下载别人的文档 | `exports` 归属表；无记录只有管理员能拿 |
| 7 | 服务器被入侵 | 拿 Key、拿客户数据 | 密钥只在 `config.json`（600）；库文件 700 |

**不在防护范围**（明确说清楚，避免误以为安全）：

- 物理接触服务器的人；
- 有 root 的人；
- 上游供应商自身的数据泄露；
- 社工（把密码告诉别人）。

## 2. 身份

### 2.1 密码

```js
// lib/identity.js
hashPassword(plain, salt)   // scryptSync(plain, salt, 32)
verifyPassword(plain, user) // timingSafeEqual 比对
```

- 每个账号独立 16 字节随机盐；
- 库里只有 `salt` + `passHash`，**没有明文**；
- 比对用 `timingSafeEqual`，避免通过响应时间推测密码前缀；
- 账号不存在、密码错误、账号没设密码 → 一律 `false`，前端收到同一句提示。

### 2.2 密码规则

| 规则 | 值 | 为什么 |
|---|---|---|
| 最短 | 8 位 | 低于 8 位在撞库面前等于没有 |
| 必须含 | 字母 + 数字 | 挡住纯数字生日 |
| 不强制 | 符号 | 强制符号会导致"写在便利贴上贴在显示器" |
| 最长 | 128 位 | 防 DoS（scrypt 对超长输入也吃 CPU） |

### 2.3 登录限流

```text
key = username.toLowerCase() + '@' + 来源IP
窗口 = 5 分钟
阈值 = 5 次失败
```

- 第 6 次直接 429，不再校验密码（省 CPU）；
- 登录成功清零；
- 账号不存在也计次 —— 否则"不计次"本身就是账号存在的信号。

## 3. 会话

| 项 | 值 | 说明 |
|---|---|---|
| 载体 | `sid` Cookie | `HttpOnly`（JS 读不到，防 XSS 偷）、`SameSite=Lax`（防 CSRF） |
| 存储 | `data/sessions.json` | 落盘，重启不掉线 |
| 有效期 | 7 天 | 滑动续期（每次请求刷新 `ts`） |
| 失效条件 | 退出 / 停用 / 过期 / 改密码 | 改密码会清掉该用户全部会话 |

**为什么落盘**：早期只在内存，重启全员掉线，给人"这系统老崩"的错觉。
落盘的代价是 `sessions.json` 要一起备份（不重要，丢了重新登录即可）。

## 4. 授权

```js
identity.canRead(me, ownerId)      // 能看
identity.canWrite(me, ownerId)     // 能改/删
identity.canManageUsers(me)        // 能管账号
```

| 角色 | canRead | canWrite | canManageUsers |
|---|---|---|---|
| owner | 全部 | 全部 | ✓ |
| admin | 全部 | 全部 | ✓ |
| member | 自己的 | 自己的 | ✗ |

**判定只在 `lib/identity.js`**。业务代码里出现 `role === 'admin'` 就是 bug
（曾经因此漏改两处，普通成员进了企业控制台）。

### 4.1 为什么越权返回 404 而不是 403

403 = "东西在，但不给你" → 攻击者可以靠 403/404 的差异枚举出"哪些 ID 存在"。
404 = "没有这个东西" → 拿不到任何信息。

### 4.2 逐对象规则

| 对象 | 读 | 写/删 | 特例 |
|---|---|---|---|
| 会话 | 自己 + admin | 自己 + admin | — |
| 资产 | 自己 + admin + **团队可见** | 自己 + admin | 共享出去只能看 |
| 上传 | 自己 + admin | 自己 | 永不共享 |
| 导出件 | 自己 + admin | — | 无记录的老文件只有 admin |
| 台账 | `ownerId` 或 `memberId` 命中 + admin | 只读 | — |
| 组织 | 全部（额度信息） | admin | — |

### 4.3 「团队可见」的边界

这是**唯一**允许跨人可见的数据通道，所以规则写死：

- 只有**成品**（图/视频/文档资产）能共享；
- **附件与导出件永远私有** —— 里面常是客户名单、未公开文案、给客户的交付物；
- 共享后同事能看能下载，`DELETE` / `share` / `fav` / `restore` 一律 404；
- 收回共享后，已发出的 `/img/xxx.png` **立刻 404**（不是"还缓存着"）。

## 5. 额度闸门

```text
① 组织余额 ≤ 0            → 402（谁都发不出去）
② 该成员 used ≥ quota     → 402（这个人发不出去，别人不受影响）
```

**闸门在建会话之前**。早期放在后面，导致"被拦住但侧栏多了一堆空会话"。

## 6. 媒体与文件

| 路由 | 内容 | 鉴权 |
|---|---|---|
| `/img/xxx.png` | 生成的图 | 登录 + 归属（或共享） |
| `/vid/xxx.mp4` | 生成的视频 | 同上（支持 Range） |
| `/file/xxx.pdf` | 上传的附件 | 登录 + **仅归属** |
| `/export/xxx.docx` | 导出的 docx | 登录 + **仅归属**（无记录→仅 admin） |

早期这四个路由**完全不鉴权**，未登录 200 就能下载全站文件（实测过）。
现在统一：`auth()` 先过，再 `mediaOwner()` 反查归属，跨人 404。

## 7. 密钥

| 密钥 | 位置 | 谁能看到 |
|---|---|---|
| 上游 `apiKey` | `config.json` → `providers[].apiKey` | 进程 |
| 方舟 `apiKey` | `config.json` → `ark.apiKey` | 进程 |
| 用户密码 | `data/db.json` → `users[].passHash` | 无人（哈希） |
| `sid` | 浏览器 Cookie + `sessions.json` | 用户自己 |

**前端永远拿不到任何 Key**：`/api/bootstrap` 只返回模型 ID 列表，不返回 Key。

`config.json` 已进 `.gitignore`。提交前自查：

```bash
git status --porcelain | grep -i config.json    # 应该无输出
git grep -nE "sk-[A-Za-z0-9]{16,}" -- . ':!docs' # 应该无输出
```

## 8. 对外试用前的检查清单

必须全部打勾才发链接：

- [ ] `config.json` 里 `auth.password` 不是示例占位串，且已登录过至少一次（触发明文迁移）
- [ ] `ls -l config.json` → `600`；`ls -ld data` → `700`
- [ ] `git status` 里没有 `config.json` / `data/`
- [ ] 外人用体验库：`SB_DATA=data-demo`、独立端口、独立账号
- [ ] 主账号密码**不能**登录体验库（`curl -X POST .../api/auth/login` 应 401）
- [ ] 体验库额度有上限（默认 20,000），用完 402
- [ ] 公网访问走 HTTPS 反代，`SB_HOST=127.0.0.1` 只让反代进
- [ ] `node scripts/verify-tenancy.mjs` 全绿（89 项越权断言）
- [ ] 有备份（至少手工 `tar czf` 一份，含 `data/` + `config.json`）

## 9. 出事了怎么办

| 现象 | 处置 |
|---|---|
| 怀疑 Key 泄露 | 立刻在上游控制台吊销 → 换新 Key → 改 `config.json` → 重启 → 查台账异常调用 |
| 怀疑账号被盗 | 停用该账号（`/api/users/:id/status`）→ 重置密码 → 该用户全部会话立即失效 |
| 发现越权 | 记录 URL + 账号 → 跑 `verify-tenancy.mjs` 复现 → 修 `canRead/canWrite` → 加断言 |
| 客户数据可能外泄 | 停服 → 备份现场 → 查 `ledger` 与访问日志 → 按合同通知 |
| 磁盘写满 | 清 `data/images`（按 `createdAt` 删旧图）→ 清 `data/exports` → 检查日志轮转 |

## 10. 已知薄弱点（诚实清单）

1. **无对话频率限制** —— 一个人连点会打满上游并发，靠额度兜底。
2. **无操作审计日志** —— 谁停用了谁、谁调了账，库里没有独立留痕（台账只有金额痕迹）。
3. **无 CSRF token** —— 依赖 `SameSite=Lax` 挡跨站 POST；如果将来放宽到 `None` 必须加 token。
4. **无内容安全过滤** —— 上传的文件不做病毒扫描；只允许白名单扩展名。
5. **无 IP 白名单** —— 管理接口对任何登录的管理员开放。
